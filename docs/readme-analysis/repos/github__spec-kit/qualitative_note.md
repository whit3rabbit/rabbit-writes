# github/spec-kit — qualitative note

Spec Kit's README reads like formal product documentation rather than a marketing pitch: a centered logo/title block, a linked Table of Contents (unusual among these five repos, and appropriate given the doc's length), and a numbered "Get Started" walkthrough where every step pairs a slash command with a literal example invocation (e.g., `/speckit.specify Build an application that can help me organize my photos...`), which makes the abstract "spec-driven development" concept concrete very quickly. Tone is neutral and precise throughout, favoring defined terminology ("Extensions," "Presets," "Bundles") each introduced with its own subsection, a priority table, and a "When to Use Which" decision table — a good example of disambiguating similar-sounding features for the reader instead of leaving them to infer differences. The doc also models good practice by separating a short conceptual "Core Philosophy" section from a much longer "Experimental Goals" research-framing section, and by explicitly noting where core project-governance guidance lives ("For existing projects, keep Spec Kit tooling updates separate from feature artifact evolution..."). It closes with conventional but complete Prerequisites, Support, Acknowledgements, and License sections — nothing flashy, but nothing missing either.

**Quotes:**
- "Spec-Driven Development **flips the script** on traditional software development... specifications become executable, directly generating working implementations rather than just guiding them."
- "Key guarantees: `info` shows exactly what `install` adds (transparency); installs are idempotent and confined to the project root..."
